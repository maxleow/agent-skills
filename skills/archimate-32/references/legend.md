# Complete view legends

Create the legend from the notation and visual conventions actually used in the view.
Include every element type, relationship type, access mode, color meaning, boundary style,
annotation identifier, and abbreviation needed to read that view.
Do not substitute a short arrow key for a complete legend.

Show a sample beside each explanation. Reuse the actual element assets, colors, line patterns,
and endpoint markers. Keep legend samples separate from model elements and relationships.
For nested membership, show a boundary sample and explain the retained Aggregation relationship.
Explain crossing gaps and whether a crossing is a connection.

Separate notation from local conventions. Layer colors are visual aids; symbols and type labels
define the elements. Colors do not imply health, errors, ownership, or deployment status unless
the view explicitly uses them for that purpose. Explain note panels and any selection highlight.
Distinguish a dashed scope border from a dashed relationship by its shape, label, and markers.

Explain numbered annotations and labels such as interface IDs. State whether they identify an
element, a cross-reference, or a sequence. Define status labels and qualify unknown placement.
Keep detailed interface contracts in their notes; the legend should explain how to find them.

Reserve readable space for the complete legend. Enlarge the canvas when required.
Provide a visible Legend control in a viewer when the full key is far from the main view.
Check that every used convention has a key entry and that each rendered sample matches its
actual style. Inspect sample markers, text bounds, and export clipping after each edit.
